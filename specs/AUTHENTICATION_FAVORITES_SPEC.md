# Tennessee Natural Landmarks Explorer
## Specification 3: Authentication and Favorites

**Status:** Approved — October 29, 2026. Sensitive-location classification criteria and initial dataset classification remain unresolved and release-blocking (see §10.3).  
**Version:** 0.3 — October 29, 2026  
**Requirements:** FR-07, FR-08; NFR 7.4, 7.5, 7.7  
**Implementation tasks:** M03-T01 through M03-T06  
**Architectural decisions:** ADR-001, ADR-002, ADR-003, ADR-006, ADR-007, ADR-008, ADR-009

## 1. Purpose and scope

Provide secure email/password account registration, sign-in, sign-out, session persistence, and per-user landmark favorites. Anonymous visitors may browse landmarks, but saving favorites and viewing a personal favorites collection require authentication. This specification also establishes reusable identity and ownership requirements for subsequent reviews and trip specifications.

**Out of scope:** account deletion, social login, OAuth providers, user roles or administration, public profiles, sharing favorites, account-based recommendations, offline favorite mutations, and password storage or custom cryptographic authentication primitives. Email verification is deferred for the initial capstone release. Secure email-based password reset is included in scope.

## 2. Non-negotiable architecture

1. Use **Better Auth** integrated with the existing Express/TypeScript backend, with database-backed sessions stored in PostgreSQL.
2. Use Better Auth's supported **Prisma adapter**. Prisma alone owns schema and migrations, including Better Auth's identity, account, session, and verification models. Do not create a redundant user table.
3. Better Auth owns password hashing, session tokens, and session-cookie lifecycle. The application implements Express integration, authentication middleware, and application-specific authorization.
4. Serve frontend and API under the same production origin, consistent with ADR-008; authentication routes live under `/api/auth/*` subject to verified Better Auth integration details.
5. Use secure, HttpOnly session cookies in production. Do not put session tokens, passwords, or credentials in localStorage, sessionStorage, or IndexedDB.
6. Never treat a client-provided user ID as proof of identity or ownership. Resolve the acting user from the validated server-side session.
7. No application code, migrations, dependency installation, or deployment changes are authorized by approval of this draft alone.

## 3. User and session data

### 3.1 User identity

- Each account has one stable internal user ID generated by the authentication system.
- Email addresses must be validated and handled using Better Auth's supported account model; email uniqueness and canonicalization must follow the verified library/database configuration.
- Collect only fields needed for registration and authentication. Optional profile information is not required for this milestone.
- Passwords are never stored in plaintext, returned by APIs, or written to application logs.
- User records referenced by favorites, reviews, or trips retain stable IDs.

### 3.2 Session behavior

- Successful login creates a usable server-validated session and sets the appropriate session cookie.
- Authenticated requests validate the session on the server; a frontend flag is never sufficient.
- Reloading the SPA should restore authenticated UI state by querying the session, not by persisting secrets in JavaScript storage.
- Sign-out invalidates the applicable session server-side, clears client authentication state, and removes authenticated controls from the interface.
- Expired, revoked, missing, or invalid sessions are treated as unauthenticated.
- Sessions expire 30 days after issuance or renewal. When a valid session is used within seven days of expiration, renew its expiration for another 30 days using supported Better Auth configuration. This is a renewable 30-day expiration interval, not a fixed absolute 30-day maximum. Ordinary sign-out revokes only the current session; a successful password reset revokes all existing sessions on all devices. Verify that the installed Better Auth version supports these semantics before implementing.

## 4. Registration, sign-in, and sign-out

### 4.1 Registration

- Provide a keyboard-accessible registration form with email, password, and password confirmation, unless the supported Better Auth integration requires a different approved form contract.
- Validate required inputs on both client and server. Server validation is authoritative.
- Require passwords of 8–128 characters without mandatory character classes; validate client-side and server-side with Zod, and enforce the same policy in the supported Better Auth configuration.
- Show useful errors without exposing stack traces, password values, account records, or session secrets.
- Registration must be subject to rate limiting and abuse protections.
- Email verification is not required for initial registration or sign-in. The application must not represent an unverified email address as verified. Successful registration may establish a session using the verified Better Auth-supported flow.

### 4.2 Sign-in

- Provide an email/password sign-in form and an explicit submission action.
- Show a generic failure message for invalid credentials to avoid unnecessary account enumeration.
- Apply rate limiting/brute-force protection, including appropriate responses when requests are throttled.
- Preserve a safe return destination when a user signs in after attempting to favorite a landmark; never accept arbitrary external redirect URLs.

### 4.3 Password reset (included in initial release)

- Provide a **Forgot password?** action on the sign-in screen and a form to request a reset email.
- Use Better Auth's supported password-reset and verification-token mechanisms; do not create custom reset token cryptography or hand-roll its identity endpoints.
- The server must send a single-use, time-limited reset link through a configured email delivery provider. **Expiry: 30 minutes**, with single-use consumption, subject to verification of the installed Better Auth configuration.
- The request form must return a neutral confirmation regardless of whether an account exists; apply rate limiting to requests and token verification.
- Reset links must use an approved application origin and must not accept attacker-controlled redirect URLs. Do not expose reset tokens in logs, analytics, referrer URLs, or third-party scripts.
- A valid reset allows a new password satisfying the approved password policy; invalid, expired, or previously used links must fail safely.
- After a successful password reset, invalidate all previously active sessions across devices. Confirm the supported Better Auth mechanism and test revocation; do not ship a weaker behavior silently.
- Use Resend or a configured Nodemailer SMTP transport; select one production provider and verified sender identity before deployment. Construct reset links from a configured canonical production origin using `/reset-password?token=...` (and any Better Auth-required validated parameters). Never derive the origin from an untrusted Host header. The reset page must prevent token leakage through logs, analytics, referrers, or third-party scripts, apply a restrictive Referrer-Policy, and remove the token from the visible URL after securely capturing it. Email delivery must be configured and tested in a non-production environment. If delivery is unavailable, the feature must report a safe failure and must not falsely claim that an email was sent.
- Email verification remains deferred; sending a password-reset email does not implicitly mark an account as email-verified.

### 4.4 Sign-out

- Provide sign-out from authenticated navigation.
- Sign-out invalidates the session and updates the UI promptly.
- A failed sign-out request must not be reported as a confirmed server-side logout.
- If the app supports offline saved landmark/trip data later, sign-out must invoke the account-scoped best-effort cleanup policy in ADR-007; do not promise complete browser-cache erasure.

## 5. Authentication and authorization boundaries

- Public discovery and public landmark profiles do not require authentication.
- Favorite listing, creation, and removal require a valid session.
- Every favorite operation is scoped by the authenticated user's server-derived ID.
- A user must never read or mutate another user's favorites, even if they guess or supply a favorite ID.
- Authentication middleware establishes identity; service/data-access logic enforces resource ownership separately.
- Protected API calls without a valid session return **401 Unauthorized**. An authenticated user requesting an inaccessible user-owned resource must not receive another user's data; use **404 Not Found** where revealing resource existence would be inappropriate.
- Authorization rules must be implemented server-side and tested with two separate user accounts.

## 6. Favorites data model and semantics

### 6.1 Data model

Create a Prisma-managed favorite relationship with:

- Stable user foreign key to the Better Auth user model.
- Stable landmark foreign key to the internal landmark primary key from Specification 1.
- Creation timestamp.
- Composite unique constraint on `(user_id, landmark_id)` to prevent duplicates.
- Referential integrity enforced by PostgreSQL.

Favorites must survive GPX updates and landmark reactivation because they reference stable internal landmark IDs. Retiring a landmark does not delete its favorite relationships.

### 6.2 Favorite actions

- An authenticated user can add an eligible active landmark to favorites.
- Repeating an add request for an already-favorited landmark is **idempotent**: it does not create a second relationship.
- An authenticated user can remove a landmark from favorites; repeated removal is idempotent.
- The UI reflects the confirmed server state, including rollback or refresh after a failed mutation.
- Favoriting a nonexistent, retired, or non-public landmark must not reveal hidden landmark details; the API returns a safe not-found response.
- A favorite list must not expose retired or restricted landmark coordinates merely because a user saved them earlier. Previously saved retired landmarks shall appear in the favorites list as a non-navigable **“No longer available”** entry without coordinates, source metadata, or other location details. The user may remove the favorite. Do not reveal sensitive or restricted details through this placeholder.

## 7. Proposed API contracts

Better Auth's registration, login, logout, and session endpoints must follow its verified supported integration under `/api/auth/*`; **do not invent or hand-implement Better Auth endpoint internals**.

Application-owned favorites endpoints:

| Method | Route | Behavior |
|---|---|---|
| `GET` | `/api/v1/favorites` | List current user's favorites |
| `PUT` | `/api/v1/favorites/:landmarkId` | Ensure landmark is favorited (idempotent) |
| `DELETE` | `/api/v1/favorites/:landmarkId` | Ensure landmark is not favorited (idempotent) |

- `:landmarkId` is the internal landmark identifier used by Specification 2; never use the GPX `source_code` as a relationship key.
- The server obtains the user ID from the validated session, never from a query parameter or request body.
- `GET` sorts by favorite creation time descending (stable tie-break by favorite ID), accepts positive integer `page` and `limit` (default 50, maximum 100), and returns a paginated envelope containing a `favorites` array of safe landmark summaries or unavailable placeholders plus pagination metadata (`page`, `limit`, `has_more`). The server must not expose another user's favorites.
- `PUT` returns `201 Created` when a relationship is newly created and `200 OK` when already present; both return `{ "success": true, "landmark_id": "..." }`. `DELETE` returns `200 OK` with the same body whether the relationship existed or not. A valid landmark ID that is no longer present in favorites may be deleted idempotently without disclosing protected landmark metadata.
- Return `400` for invalid landmark ID syntax, `401` for unauthenticated requests, `404` for nonexistent or unavailable landmarks, and `429` for throttled requests when applicable.
- Unexpected server errors return safe `5xx` responses without implementation details.
- Use a consistent error envelope with a machine-readable code and human-readable message; final shared API envelope should align with Specification 2.
- A favorite mutation is atomic at the database level and safe against concurrent duplicate requests.

## 8. Frontend behavior and accessibility

- Public landmark cards and profiles show a recognizable favorite action; activating it while signed out offers sign-in rather than silently failing.
- Signed-in users see the current saved/unsaved state and can toggle it.
- A dedicated **My Favorites** view lists saved landmarks and supports removal and navigation to public landmark profiles.
- An empty favorites collection displays an informative empty state and a way back to discovery.
- Retired favorites appear as non-navigable “No longer available” entries with a removal action and no location details; they must not link to retired landmark profiles.
- During requests, show pending feedback and prevent confusing duplicate submissions.
- On authentication expiry, explain that sign-in is required and preserve the current public discovery context.
- Do not imply a favorite was saved until the server confirms it; if optimistic updates are used, revert them on failure.
- Buttons have accessible names and state (e.g., `aria-pressed` or equivalent), visible keyboard focus, and usable screen-reader feedback.
- Form fields have explicit labels, validation feedback, and no keyboard traps; meet the project's WCAG 2.2 AA target.
- Favoriting must not disturb the URL-based discovery state defined in Specification 2.

## 9. Security, privacy, reliability, and acceptance tests

### 9.1 Security controls

- Use HTTPS in production, Secure and HttpOnly cookies, and an appropriate SameSite policy.
- **Explicit CSRF protection is required** for cookie-authenticated state-changing requests. In production, require an exact allowed-origin match for `Origin` on state-changing requests, reject mismatches and `Origin: null`, and use a validated same-origin `Referer` fallback only where appropriate. Reject requests lacking trustworthy origin evidence unless a verified Better Auth-specific CSRF mechanism explicitly handles the route. Configure session cookies `Secure`, `HttpOnly`, and `SameSite=Lax` (or `Strict` if compatible). Apply compatible protections to Better Auth mutation routes and test their actual behavior; cookie flags alone are insufficient.
- Enforce login and registration rate limits/brute-force protections; verify that the selected storage mechanism behaves appropriately in the deployed environment.
- Do not expose password hashes, session tokens, authentication secrets, or database credentials in API responses, logs, error messages, or client-side persistence.
- Avoid account enumeration and unsafe redirect destinations.
- Do not enable permissive credentialed CORS. The approved production deployment is same-origin; revisit CORS only if the deployment topology changes through approval.

### 9.2 Required automated tests

Use Vitest, Supertest, a dedicated test PostgreSQL database, React Testing Library, and Playwright in accordance with ADR-009. Authentication integration tests must use real HTTP requests and real session cookies rather than only mocked users.

1. Valid registration and login establish an authenticated session without requiring email verification.
2. Invalid credentials fail safely; throttling protects repeated attempts.
3. Missing, expired, forged, and revoked sessions cannot access favorites.
4. Logout invalidates the relevant session; subsequent protected requests fail.
5. CSRF protection rejects inappropriate state-changing requests.
6. User A cannot list, add, or delete User B's favorites by manipulating identifiers or payloads.
7. Duplicate and concurrent favorite-add requests produce one relationship.
8. Repeated favorite deletion does not expose or delete another user's data.
9. Favorite references survive landmark metadata reimport and retirement/reactivation.
10. Favorites responses honor public landmark visibility and sensitive-location restrictions.
11. Sign-in, sign-out, favorite toggling, empty states, error feedback, and keyboard access work in the UI.
12. Password-reset requests do not disclose account existence; email delivery is tested with a controlled test transport.
13. Valid reset tokens work once; expired, invalid, and reused tokens fail safely; reset-request throttling is enforced.
14. Successful reset applies the 8–128 character password policy and revokes all existing sessions across devices; standard sign-out revokes only the current session.
17. Session expiration and renewal conform to the approved 30-day / seven-day policy.
18. Favorites pagination, newest-first ordering, 201/200 PUT behavior, and idempotent 200 DELETE responses are verified.
19. CSRF tests reject foreign, null, and untrusted missing origins for state-changing routes.
20. Reset links are single-use, expire after 30 minutes, use the canonical origin, and do not leak tokens via browser referrers or logs.
15. Retired favorites appear only as non-navigable “No longer available” entries, omit location details, and can be removed.
16. Automated tests use a dedicated database, not the live Render database.

## 10. Approved decisions and implementation verification

### 10.1 Decisions approved for this revision

1. **Email verification:** Deferred for the initial capstone release. Registration and login must not require a verified email. This does not authorize labeling unverified addresses as verified.
2. **Password reset:** Included in the initial release as a secure email-based flow using Better Auth-supported mechanisms. An email delivery provider and supported token/session configuration must be selected before implementation.
3. **Retired favorites:** Display a non-navigable **“No longer available”** entry without coordinates or location metadata, with an option to remove the saved favorite.

### 10.2 Decisions adopted for v0.3

1. **Password policy:** 8–128 characters, no arbitrary complexity requirements; client and server Zod validation, aligned with supported Better Auth behavior.
2. **Sessions:** Renewable 30-day expiration interval; renew when used within seven days of expiry. Ordinary sign-out revokes the current device session; successful password reset revokes all prior sessions.
3. **Password reset:** Single-use 30-minute token; Resend or Nodemailer SMTP; canonical configured `/reset-password?token=...` link; prevent token leakage. Select provider and sender identity before deployment.
4. **Favorites API:** Newest-first, stable pagination (`page` default 1, `limit` default 50, maximum 100); paginated `favorites` envelope. PUT responds 201 for new, 200 for existing; DELETE responds 200 idempotently. Both mutation response bodies contain `success` and `landmark_id`.
5. **CSRF:** Exact same-origin checks with validated Referer fallback and fail-closed behavior, plus Secure/HttpOnly/SameSite cookies and Better Auth route compatibility.
6. **Account lifecycle:** Account deletion is out of scope for the initial release. Any later addition requires a separately approved deletion/anonymization policy for favorites, sessions, reviews, and trips; no future cascade behavior is authorized by this draft.

### 10.3 Verification and unresolved cross-specification dependencies

- Confirm actual Better Auth version/configuration supports the approved renewal, session revocation, reset expiry, and origin checks. If not, stop and request a decision rather than silently weakening requirements.
- Select and configure the production email delivery provider and verified sender identity before release.
- Resolve sensitive-location disclosure across Specifications 1–3 before publicly exposing restricted locations or saved restricted landmarks.
- Align shared error envelopes and landmark ID format with Specification 2.
